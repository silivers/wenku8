## 修复 database is locked（多线程爬取章节丢失）

### 根因（从用户真实日志 DB-LOCK-DIAG 定性）
- 日志特征：所有失败是**同一条连接（conn_id=d90f0a0b / Thread-3）在 10:56:11 同一瞬间**批量报 `database is locked`；`busy_timeout=30000 journal_mode=wal` 已生效（PRAGMA 落到连接上）；`wal_size=70072`（仅 70KB，非 checkpoint 阻塞）。
- 结论：`busy_timeout` **只对 SQLITE_BUSY 自旋等待，对 SQLITE_LOCKED（死锁规避，瞬时返回）无效**。多线程并发写时，一个连接持有写事务、另一连接想「读→写升级」会立刻拿到 SQLITE_LOCKED，busy_timeout 兜不住。
- 真正缺口：上轮加的诊断代码 `_exec` **只诊断、不重试**——INSERT 首次冲突即 `raise`，章节被记为失败；而 `_commit_retry` 只对 commit 路径重试，失败的 INSERT 在 `_exec` 路径上没被覆盖。

### 改动（`novel/storage/sqlite_backend.py`）
- 新增 `_run_with_lock_retry(fn, sql, params)`：对 `lock`/`busy` 类 `OperationalError` 做指数退避重试（25 次，退避 `min(0.02*2**n, 0.5s)`），仅最终耗尽才 `_diag_lock` 抛错。
- `_exec` / `_executescript` 改为经 `_run_with_lock_retry` 包装（**修复点**：执行路径也重试，与 commit 路径对齐）。
- `_commit_retry` 重构为复用 `_run_with_lock_retry`（同时覆盖 `busy`，不再只认 `locked`）。
- 类常量 `_LOCK_MAX_RETRIES=25` / `_LOCK_BACKOFF_BASE=0.02`。

### 验证
- 确定性单测：前 3 次抛 locked、第 4 次成功 → 返回结果（calls=4）；持续 locked → 超限抛错；非锁错误 → 立即原样抛出不重试。ALL PASS。
- 多线程集成测试（2 worker × 4 轮 × 3 并发，SELECT→INSERT 模式）：**24/24 行零丢失，0.1s**。
- `py_compile` 全过；`pytest` 12 passed。
- 注：零网络延迟的极端并发测试会把 SQLite 写锁完全串行化而变得极慢（非 bug，生产里每章抓取是网络秒级、写锁只持毫秒）。临时测试文件已清理。

- 登录：`sites login` + `crawl`/`crawl-all`/`update` 的 `--username/--password` + 环境变量 `WENKU8_USERNAME`/`WENKU8_PASSWORD`。

## database is locked 彻底修复（autocommit + 短事务 + 小 busy_timeout）

### 上轮为何未根除
上轮只给执行路径加了重试（`_run_with_lock_retry`），但用户重跑仍 25 次重试全失败后落 DB-LOCK-DIAG。说明这不是"瞬时冲突"，而是**有连接长时间持有写锁**。

### 三层根因（最终定性）
1. **【真正主因】aiosqlite 默认 `isolation_level=""`（autocommit off）**：每次 `SELECT` 都开读事务且**不自动关闭**。`crawl_novel` 用 `asyncio.gather` 并发跑多个 `save_chapter`，同一连接上堆叠多个"永不关闭的读事务"，使该连接的写升级（INSERT）不断触发 `SQLITE_LOCKED`（busy_timeout 对 LOCKED 无效）→ 重试耗尽。
2. **【长事务】M3「批量一次性 commit」优化**：`save_chapter`/`save_image` 不提交，整本小说所有 INSERT 攒到 `crawl_novel` 末尾才 commit。WAL 单写者下，写锁被该 worker 横跨几十秒网络抓取长期独占，饿死其他 worker。
3. **【livelock】`busy_timeout=30000`**：多线程 writer 竞争下，把每次写冲突放大成 SQLite 内部自旋等待 30s（日志出现 32s 间隔），退化为类 livelock。

### 改动（`novel/storage/sqlite_backend.py`）
- `init()` 的 `aiosqlite.connect` 加 `isolation_level=None`（真正 autocommit）：每条 SELECT/INSERT 自动提交，消除残留读事务 → **根除 LOCKED 的关键**。
- `save_chapter` / `save_image` 末尾加 `await self._commit_retry()`（每章/每图短事务）：写锁持有降到毫秒级。
- `busy_timeout=30000 → 200`、`connect timeout=30.0 → 5.0`：冲突快速失败，交给我方 `_run_with_lock_retry` 退避重试兜底（消除 30s 自旋）。

### 验证
- 多线程集成测试（6 worker × 8 轮 × 6 并发 gather，真实 SQLiteBackend.save_chapter + 短事务 + autocommit）：**288/288 行零丢失，无 DB-LOCK-DIAG**，仅偶发 1 次瞬态 DB-RETRY（退避 0.02s 后重试成功）。
- `py_compile` 全过；`pytest` 12 passed。
- 临时测试文件 _verify_fix.py 已删；data/ 下残留数个 `_verify_fix_*.db*` 测试库（sandbox 安全删除拦截未清，不影响主库 novels.db）。

用户线上日志：多线程爬取时章节/全站/图片下载三处同时秒级爆 `database is locked`（非 30s 超时）。

### 已加诊断（`novel/storage/sqlite_backend.py`）
- `init()` 加 `connect(timeout=30.0)` 双保险（PRAGMA 万一失效仍有 sqlite3 busy handler）。
- `init()` 末尾回读并打印 `DB-INIT | conn_id=.. thread=.. busy_timeout=.. journal_mode=.. synchronous=..`——确认 PRAGMA 真生效。
- 新增 `_exec`/`_executescript` 包装，替换全部 `self.conn.execute/executescript`；遇 `locked` 调 `_diag_lock`。
- `_diag_lock` 打印 `DB-LOCK-DIAG`：conn_id、线程、忙超时/日志模式回读、db_size/wal_size、出错 SQL（截断）、参数、ACTIVE_THREADS、调用栈末 10 帧。

- 结论：线上秒级锁来自比复现更重的负载（疑似长事务跨网络 I/O 撑开 / WAL 撑大后 checkpoint 被阻塞，此类锁 busy_timeout 兜不住）。待用户重跑日志看 `DB-LOCK-DIAG` 的 `wal_size` 与出错 SQL 定性，再定修复（缩短事务 / 降 `wal_autocheckpoint` / 周期 `wal_checkpoint(TRUNCATE)`）。

## shard 升级：work-stealing 块队列（方案 C，替代静态等分）

用户问「流程是否 = 上界 8000、每线程 2000」并选方案 C。旧实现 `_run_shard` 静态等分：`upper = stored if stored else 8000`，`span=(upper-start+1)//N`，每 worker 固定段。三个问题：① 上界 8000 是过时猜测 → 首次 shard 漏爬 8000 外；② ID 空洞分布不均 → 负载失衡；③ 硬边界无自适应。

### 改动（`novel/engine/worker_pool.py`）
- 删除 `DEFAULT_SCAN_UPPER=8000`，新增 `BLOCK_SIZE = 2000`。
- `_run_shard`：去掉 probe/stored/upper/span/segments，改为初始化共享状态（`_next_block_id`/`_steal_done`/`_blank_prev`/`_global_last_valid`，全由 `_lock` 保护）。
- `_worker_loop_stealing`（替代 `_worker_loop_shard`）：原子领取 `[s, s+BLOCK_SIZE)` 块 → `_scan_block` 扫描+爬取 → 末尾判定：连续两个整空白块（块内 0 有效小说）→ `_steal_done=True`，由确认者写 `set_last_novel_id(全局最后有效 ID)`。
- `_scan_block`：`iter_all_novels({"start_id": s, "end_id": s+BLOCK_SIZE-1})` 逐个 `engine.crawl_novel`，返回块内最后有效 ID（无则 None）；复用「连续 100 无效页提前终止」语义。
- `max_novels` 改为全局上限（原为每段 per）。

### 关键语义（重要，勿踩坑）
- **「连续 100 空洞 = 末尾」是 wenku8 站点假设**：iter_all_novels 遇 100 连续空洞即提前终止。work-stealing 用「连续两块整空白（≈4000 空洞）」判定末尾，比单线程 100 阈值更保守，不会误停。真实站点下架零散（不会 100 连号），块内不会因中途空洞漏扫；打桩测试必须模拟「稀疏空洞 + 末尾连续空洞」，否则提前终止会漏（曾用 999 连续空洞的极端用例误判）。
- 块内提前终止时块后部不扫（与单线程语义一致，非 work-stealing 引入）。

## 分块领取逻辑定稿（用户 2026-08-19 新方案，替代整块 work-stealing）

用户明确方案：外层固定 500 一本分块（1-500、501-1000…），**所有线程在块内完成任务**——
块内按「序号最低的空闲书号」单本粒度原子领取（如 4 线程：领 1/2/3/4，1 号完成后领 5，2 号领 6…），
整块领完切下一块；**单个整空白块**（块内 0 有效）即结束，最后有效书号 = 网站总书数。

### 改动（`novel/engine/worker_pool.py`）
- `BLOCK_SIZE`：2000 → **500**（块级常量，块内为单本粒度）。
- `_run_shard`：共享状态改为 `_block_start/_block_end/_next_block_id/_block_valid/_steal_done/_global_last_valid`（全 `_lock` 保护）；去掉原连续两块空白判定（`_blank_prev`）。
- `_worker_loop_stealing` 重写：块内原子领单本书号（`_next_block_id` 自增）；越过块尾时收尾——`_block_valid==0`（整空白块）→ 置 `_steal_done` 并写 `last_novel_id`，否则切下一块；锁外 `crawl_novel(str(nid))`，**ValueError = 无效书号**（空白信号），其余异常 = 失败（不算空白）。
- 删除 `_scan_block`（被块内单本逻辑取代）。

### 关键语义（勿踩坑）
- 无效书号判定依赖 `crawl_novel` 内 `get_novel_info` 抛 `ValueError("小说 ID X 不存在或已下架")`。
- 失败（网络）≠ 空白：失败书号计入 `_block_valid`（valid=True），防误判空白块提前结束。
