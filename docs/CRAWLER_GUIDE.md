# 爬虫开发注意事项（CRAWLER_GUIDE）

> 一份通用的爬虫/采集程序开发避坑清单，提炼自一个真实的多线程爬虫项目
> （2026-08）踩过的坑与修复。每条 = 一句话场景 + 通用原则，可直接套用到
> 你自己的爬虫、数据管道或带断点续爬的采集程序。

---

## A. 页面编码——按实际字节解，别信声明

**场景**：网页 `meta` 声明一种编码，实际内容却是它的超集（扩展字符）；
按声明解码直接报错，解码失败后随手回退成 UTF-8，又得到一堆乱码，
还被"乱码检测器"误判成数据损坏。

**原则**
1. 解码走**编码链**：声明编码 → 同族的超集（比如 GB 系一律试 GB18030）→
   UTF-8 保底。解码失败**先试同族超集，别直接跳 UTF-8**。
2. 以**实际字节**为准——页面声明的编码只当第一候选。
3. 乱码检测看"解码后的替换符数量"，不要凭"用了哪个编码"下结论。

## B. 异常/下架判定——用少见的精确信号，别拿公共文本当特征

**场景**：想识别"资源被删除/下架"的页面，随手抓了个特征——结果那个特征
（版权声明、页脚、广告位）**每个正常页面都有**，于是所有正常资源都被误判
成异常，静默跳过一大片。

**原则**
1. 异常判定用**出现频率低、语义明确**的信号（精确文案、特定 DOM 结构），
   绝不用"每页都有的公共文本"。
2. 宁可**漏判**不可**误杀**——漏判最多多请求一次，误杀是悄悄丢数据。
3. 判定逻辑收敛成一个函数（如 `is_removed()`），集中维护、便于测试。

## C. URL 与路径——验证边界值，生成逻辑只留一处

**场景**：资源路径带编号，比如 `/detail/{x}/{id}/` 的 `x` 是按 `id` 算出来的
分桶值。用小 id 测一切正常，等 `id` 超过分桶阈值，全部 404——因为只在
小编号上验证过规则。

**原则**
1. 路径/URL 模板必须用**边界值**验证：最大 id、跨桶 id、带特殊字符的 id。
   小值通过不算数。
2. URL 生成收口到**一个函数**，业务代码里禁止散落拼接——改一处全局生效。
3. 用**真实抓页**确认规则，别靠推测。

## D. 数据库并发写——autocommit + 短事务 + 小 busy_timeout

**场景**：多线程并发往同一个 SQLite 写数据，一会儿 `database is locked`、
一会儿丢数据。逐层排查后发现四个叠加原因：
- 连接默认没开 autocommit，每次 SELECT 都留下一个不关的读事务，
  并发写时"读转写"直接被锁拒绝（而这个锁类型 busy_timeout 根本不管用）；
- 攒着批量提交，写锁被几十秒的网络抓取横跨独占，其他线程全部饿死；
- busy_timeout 设成 30 秒，冲突时每个线程都在 SQLite 内部自旋等 30 秒，
  退化成一堆线程互相等（livelock）；
- 多个线程同时连接一个"还不存在"的库，初始化语句互相锁死。

**原则**
1. 连接用**真 autocommit**（如 `isolation_level=None`），消灭残留读事务。
2. 写操作**即写即提交**（短事务），写锁只持毫秒级；
   绝不在"抓完一大批再统一 commit"。
3. busy_timeout 用**小值**（200ms 量级），冲突快速失败，
   交给应用层指数退避重试（封顶半秒）兜底——大 busy_timeout 是 livelock 温床。
4. 建库/迁移/初始化用**全局锁**串行化，只有第一个线程做。
5. 锁冲突重试要同时覆盖**执行语句**和**提交**两条路径，
   失败时打印现场（PRAGMA 回读、文件大小、活跃线程、调用栈）——
   并发问题不可观测就永远修不好。

**细节：PRAGMA 是"每条连接"生效的**
`busy_timeout`、`journal_mode` 这类 PRAGMA 落在**单个连接**上，不是全局的——
多线程每个连接都要设一遍。设完还要在启动日志里**回读确认**
（`PRAGMA busy_timeout` 能查到 200 才叫生效），否则你以为设了、实际没有，
排查时白费半天（本项目曾靠"DB-INIT 日志回读"定位到 busy_timeout 没落上）。

## E. 幂等与断点续爬——去重约束 + 差集 + 进度语义分离

**场景 1**：断点续爬靠"已存在就不爬"，但站点里的资源 id（比如章节号）
是**局部命名空间**——每个上级对象下都有 "1"、"2"。去重查询没带上上级 id，
于是 B 对象的 "2" 被 A 对象已爬的 "2" 误判为已处理，悄悄跳过。

**场景 2**：记录"我爬到哪了"用了一个最后编号。但"爬过"≠"爬完"——
某次网络抖动让一个资源只成功了一半，它还是被计入进度；下次续爬
从这个编号之后开始，这个半成品**永远不会被补齐**。

**原则**
1. "是否已处理"的查询必须带上**全部维度主键**（上级 id + 自身 id），
   不能只匹配局部字段。
2. 数据库加 `UNIQUE` 约束 + `INSERT OR IGNORE`（或 `ON CONFLICT`），
   写入天然幂等，重跑零副作用。
3. 批量去重用一条 `IN` 查询，别 N+1 逐条查。
4. 进度（游标/最后 id）与内容完整性是两码事：收尾前**重扫**失败项
   （差集幂等），仍失败的把进度**回退**到它之前——宁可下次重扫，
   不可永久漏。

**细节：续传序号到底 "+1" 还是 "+0"？**
1. **先把游标语义写清楚**。两种惯例都行：存"最后一个已完整处理的编号"
   （续传起点 = 它 + 1），或存"下一个待处理的编号"（续传直接用）。
   选定一种后在代码和文档里写死，**别混用**——最隐蔽的 bug 就是
   "这里 +1 那里没 +1"，续传多爬一条或漏一条。
2. **游标只在"整轮完整收尾"时更新**，异常中断时绝不更新。
   如果边处理边推进游标，中断前"爬到一半"的那个资源会被记成已处理，
   下次续传从它之后开始，**它的剩余部分永远不会被补齐**。
   中断不更新游标 = 下次从头重扫中断后的那一段（配合差集幂等，
   代价只是重复目录请求，换来的是不丢数据）。
3. **推进游标的条件是"内容完整"，不是"被处理过"**。某个资源只成功了一半，
   即使半截也把编号算进游标，下次就不经过它了——半成品永久缺块。
   收尾时要重扫"处理过但不完整"的项（差集幂等，只补缺失部分）；
   重扫后仍不完整的，把游标回退到它之前（下次从头再试，网络恢复自动补上）。

**细节：去重键要选全维度**
`UNIQUE` 约束的键缺一个维度，就会把"不同资源"当成"同一个"——比如只按
远程地址去重，同一地址出现在两个不同上级下就会互相吞。键要覆盖
"业务上唯一"所需的**全部维度**（上级 id + 资源 id）。另外 `INSERT OR IGNORE`
是**静默丢弃**的：重复时不报错也不返回，别用它承载"必须插入成功"的写入
（此时你根本不知道被吞了）。

**细节：批量查询的占位符有上限**
`IN (?,?,...)` 一次绑定的参数数量受数据库上限约束（SQLite 约 999 个），
超长列表要**分批**查询再合并结果；列表为空时还要特判跳过（空 IN 是语法错误）。

## F. 失败重试——独立阶段 + 状态机 + 收敛兜底

**场景**：图片/附件这类"大概率会失败"的资源，和正文一起在一条链路里下载。
网络一抖，失败的资源被静默丢弃，没有重试入口，数据永久缺块。

**原则**
1. 易失败且可独立重试的资源与主链路**解耦**：主流程只"登记"
   （入库 pending），下载由独立阶段驱动。
2. 用**状态机表**管重试：`pending → done / failed →(下一轮) done`，
   用 `attempt_count` 记尝试次数。
3. 重试必须**收敛**：达到上限仍失败就置终态（如 `skipped`）——
   否则死链会让任务永远跑不完（"直到全部成功"要收敛成"成功或跳过"）。
4. 轮次不需要单独建表，`attempt_count` 本身就表达"第几轮"。

**细节：错误要分流，别一视同仁地重试**
HTTP 404/资源不存在 = "这个资源确实没了"，重试多少次都一样，属于
**正常失败**（记一笔即可）；网络超时、5xx 才是**值得重试**的错误。
按错误类型决定"要不要重试、记不记失败"，否则死链会一直耗到重试上限。

**细节：文件类型用内容头探测，不信 URL 后缀**
下载到的文件扩展名按**内容头（魔数）**判断（PNG/JPEG/GIF 各有固定字节头），
别信 URL 后缀——很多地址长这样 `/image.php?id=1`，根本没有后缀。
判断不出时再拿 URL 兜底猜一个，最后统一回退一个默认值。

## G. 多线程加速——每 worker 私有实例，跨线程只传标量

**场景**：想用多线程提速，但框架是 asyncio（单线程事件循环），
限速锁也是"每实例一把"。直接开多线程发现速度没变，甚至被锁串行化。

**原则**
1. 提速的正确姿势：**N 个线程 × 每个线程独立的完整实例**
   （独立事件循环、独立 HTTP 客户端、独立限速器）——限速预算翻 N 倍，
   整体仍合规（不是破限速，是横向扩展）。
2. 所有"绑定单一线程"的对象（连接、客户端、锁、适配器）**只在本线程内
   创建使用**；跨线程只传不可变标量（id、路径）。
3. 用**工厂**给每个线程发新实例，禁用共享单例。
4. 唯一共享的东西：有界任务队列、锁保护的统计、并发安全的数据库
   （配合 D 节）。
5. 任务分配用**分块领取**（谁空谁拿、块内单本粒度），比静态均分好——
   数据空洞分布不均时静态段会负载失衡。
6. "是否到末尾"的判断要**保守**（比如整个空白块才算结束），
   避免中途成片的空档被误判成终点。

## H. 配置化与可观测性——参数入配置，展示生效值

**场景**：站点限速这类参数写死在代码里（比如 5 秒）。用户改配置文件，
发现毫无效果——因为程序内部取的是 `max(代码写死值, 配置值)`，
配置只能调大不能调小；而且"查看站点列表"显示的还是代码写死值，
跟配置完全脱节，用户以为配置坏了。

**原则**
1. 所有可调参数（限速/线程/并发/重试阈值）**集中在配置文件**，
   生效值 = 配置 > 站点默认 > 代码兜底；改配置即生效，**不写死生效值**。
2. "展示"类命令（站点列表、配置查看）必须显示**最终生效值**，
   否则用户永远以为配置没生效。
3. 程序可以内置保护性下限（防封），但**必须允许配置覆盖**并提示风险，
   不能静默强制。
4. 留观测入口：配置查看、状态命令、失败诊断日志。

**细节：帮助文本/文档注释要与实现同步**
删了参数、改了默认值、换了行为，`--help` 的说明、docstring、README 里的
示例**必须一起改**——旧示例会直接误导用户按过期用法操作（本项目曾删掉
`--workers` 参数后 docstring 里还留着它，用户照着敲就报错）。把
"改代码必查帮助文本"当成改动的收尾步骤。

## I. 数据一致性——写入时定型，一份数据只存一处

**场景**：同一个数据（图片元数据）存了两份：一张业务表 + 一个 JSON 字段，
两处还经常对不上；而导出功能只信其中一份。查半天才明白双轨存储
是罪魁祸首。

**原则**
1. 一份数据只存**一处**，或明确指定谁是"事实来源"。
2. 在**写入时定型**：下载成功就把远程地址回写成本地路径——
   数据库里的内容就是最终形态，消费方（导出器/预览）零解析逻辑。
3. 回写要**全量幂等**：按主键做替换，对已处理内容是 no-op；
   不要按局部条件回写（同一个地址出现在多处时会漏）。
4. 存量脏数据迁移：**宁可重下重爬**也别维护复杂的脏数据合并逻辑——
   评估成本时把"数据到底可不可信"算进去。

## J. 其他小细节

1. **路径安全**：拿外部字符串拼文件路径前必须净化
   （只保留字母数字和下划线），防路径穿越。
2. **文件命名约定**：消费方只认固定扩展名（如封面固定 `.jpg`），
   落盘按约定写，别用探测结果随意改扩展名。
3. **文件名补零保证排序**：序号用 `img_0001` 而不是 `img_1`——
   否则字典序里 `img_10` 排在 `img_2` 前面，遍历/拼 EPUB 时顺序就乱了。
4. **路径拼接用 pathlib**：别用字符串拼路径（Windows `\` 与 Linux `/`
   不一致）；`Path / 子路径` 自动处理分隔符，换平台零改动。
5. **登录态**：会话 Cookie 写共享 HTTP 客户端，全链路自动携带；
   账号密码只从命令行参数/环境变量读，不落配置文件。
6. **版本化迁移的细节**：
   - 迁移文件名**零填充**编号（`001_`、`002_`…），否则 `10_` 会排在
     `2_` 前面导致顺序错乱；按编号升序执行，记录已应用版本。
   - `ALTER TABLE ADD COLUMN` 必须带 `DEFAULT`——否则**存量行**的新列全是
     NULL，老数据的兼容逻辑要在查询里兜底。
   - 数据库 DDL 大多**不支持事务回滚**，执行迁移前先备份数据文件。
   - 多线程场景下建库/迁移要用**全局锁**串行化（同 D 节），
     只有第一个连接真正建库，其余等库就绪。
7. **无测试套件时的验证**：用"离线打桩 + 一次性验证脚本"
   （本地 HTTP 服务模拟成功/失败/404、假适配器模拟网络抖动），
   跑完删掉脚本；改完至少跑一遍语法编译兜底。
8. **职责边界**：站点知识（解析、URL、限速声明）全放适配器层，
   框架只做调度、存储、重试、并发——换站点只写适配器，
   核心链路自动可用。
